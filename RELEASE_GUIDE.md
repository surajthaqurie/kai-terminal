# Production Release & Deployment Guide

This guide details code signing configuration, installer generation, GitHub Release deployment, and pre-release verification.

---

## 1. Code Signing & Notarization

To avoid operating system security warnings (Windows SmartScreen, macOS Gatekeeper), release binaries should be signed prior to distribution.

> [!IMPORTANT]
> **Secrets Security:** All certificates, passwords, and private keys must be stored strictly in GitHub Repository Secrets. No secret keys or certificates should ever be committed to the repository.

### 1.1 Windows Code Signing (Authenticode)
- **Certificate Format:** Base64-encoded `.pfx` certificate.
- **GitHub Action Secrets:**
  - `WINDOWS_CERTIFICATE`: Base64 string of `.pfx` file.
  - `WINDOWS_CERTIFICATE_PASSWORD`: Password for `.pfx` file.

### 1.2 macOS Code Signing & Notarization
- **Certificate Format:** Apple Developer ID Application (`.p12`).
- **GitHub Action Secrets:**
  - `APPLE_CERTIFICATE`: Base64 string of `.p12` developer certificate.
  - `APPLE_CERTIFICATE_PASSWORD`: Password for `.p12` certificate.
  - `APPLE_ID`: Apple Developer account email.
  - `APPLE_PASSWORD`: App-specific password generated on appleid.apple.com.
  - `APPLE_TEAM_ID`: 10-character Apple Developer Team ID.

### 1.3 Tauri Updater Signing (Optional)
- **GitHub Action Secrets:**
  - `TAURI_SIGNING_PRIVATE_KEY`: Private key generated by `tauri signer generate`.
  - `TAURI_KEY_PASSWORD`: Key passphrase.

### 1.3a In-app update signing (required for in-app updates)
The in-app updater installs an update only if it verifies against a public key compiled into the app (see `SECURITY.md`, "Updater integrity"). Each release must therefore carry `SHA256SUMS` and `SHA256SUMS.sig`; `scripts/sign-release-checksums.sh` creates them in the `publish` job of `release.yml`.

- **GitHub Action Secret:** `UPDATE_SIGNING_KEY` = the Ed25519 private key in PKCS#8 PEM form (the whole file, including the `BEGIN`/`END` lines). Without it the release still publishes but is **not** installable from inside the app (users install from the release page); a key that does not match the public key compiled into the app fails the signing step.
- **Expected secret format, exactly:** the file `openssl genpkey -algorithm ED25519` writes. Three lines: `-----BEGIN PRIVATE KEY-----`, one base64 line, `-----END PRIVATE KEY-----` (about 119 bytes). The signing step checks this first and fails with a specific message, never echoing the key, for:
  - a passphrase-protected key (`BEGIN ENCRYPTED PRIVATE KEY`): CI cannot type a passphrase; store `openssl pkey -in key.pem -out plain.pem` instead;
  - an OpenSSH key (`BEGIN OPENSSH PRIVATE KEY`), a public key, or a raw hex/base64 seed: not a PKCS#8 private key;
  - a PEM pasted as one line (line breaks lost): paste the file as it is. Windows line endings are fine.
  `src/__tests__/signReleaseChecksums.test.ts` runs the real script against throwaway keys for each case.
- **Setting it:** `gh secret set UPDATE_SIGNING_KEY < update-signing-key.pem` keeps the line breaks (or paste the whole file into Settings → Secrets and variables → Actions). Before setting it, check the pair matches the app: `openssl pkey -in update-signing-key.pem -pubout -outform DER | tail -c 32 | od -An -tx1 | tr -d ' \n'` must print exactly the contents of `src-tauri/update-public-key.hex`. Then delete the local file.
- **If the private key is lost before any release embeds its public key** (true as of v0.2.3, which predates update verification): generate a new pair with the commands below and commit the new `update-public-key.hex`; nobody is locked out. After a release has shipped the key, losing it means installed apps can only be updated by hand once (ship a build with a new key from the release page).
- **Public key:** `src-tauri/update-public-key.hex` (32 raw bytes as 64 hex characters), compiled into the app. It is public and committed.
- **Create or rotate a key pair:**
  ```bash
  openssl genpkey -algorithm ED25519 -out update-signing-key.pem          # keep private; becomes the secret
  openssl pkey -in update-signing-key.pem -pubout -outform DER | tail -c 32 | od -An -tx1 | tr -d ' \n' > src-tauri/update-public-key.hex
  ```
  Store the PEM only as the repository secret (delete the local file). **Rotation:** first ship an app build that embeds the NEW public key, signed with the OLD key (so installed apps accept it); only then switch the secret. Switching both at once locks every installed app out of in-app updates.
- **Check a release:** it must list `SHA256SUMS` and `SHA256SUMS.sig` next to the installers. To check a published release against the key shipped in the app: download `SHA256SUMS` and `SHA256SUMS.sig` into a folder, then `KAI_TEST_SIGNED_RELEASE_DIR=<folder> KAI_TEST_SIGNED_RELEASE_FILE=<an installer name from SHA256SUMS> cargo test --manifest-path src-tauri/Cargo.toml --test update_verify openssl`.
- The version in the release tag must be higher than the running app's: the updater refuses anything that is not strictly newer.

### 1.4 Microsoft sign-in app (Azure DevOps and Teams)
- **GitHub Action Variables** (public IDs, so *variables*, not secrets):
  - `KAI_AZURE_CLIENT_ID`: Application (client) ID of Kai's multi-tenant Entra app. Covers Azure DevOps and, unless overridden, Teams.
  - `KAI_TEAMS_CLIENT_ID` (optional): a separate Teams-only app.
  - `KAI_REQUIRE_SIGNIN_APP` (optional): `1` fails a release build that has no ID. Set it once the ID exists.
- Registration steps: `docs/azure-devops-sign-in.md` and `docs/teams-sign-in.md`. A malformed ID fails the build.
- Check after release: `kai integration azure` and `kai integration teams` open the Microsoft sign-in page with no "not set up" message.

### 1.5 Bundled Node.js runtime
- The installers carry their own Node.js for the bundled `kai` CLI. The version is the single line in `scripts/bundled-node-version.txt` (currently the Node 24 LTS line, the one CI runs the tests on). `scripts/fetch-node.mjs` downloads it during the release build and refuses it unless its SHA-256 matches nodejs.org's `SHASUMS256.txt`; `KAI_NODE_VERSION` overrides the pin for a local experiment.
- CI, the release build and `Dockerfile.test` compile with one exact Rust version, the single line in `scripts/rust-toolchain-version.txt`. Local builds use whatever toolchain you have (there is deliberately no `rust-toolchain.toml`: on Windows rustup would install the MSVC variant for it, which breaks GNU-toolchain machines). To move to a newer Rust, change that file, every `toolchain:` line under `dtolnay/rust-toolchain` in `.github/workflows/*.yml` and `--default-toolchain` in `Dockerfile.test`; `workflowPinning.test.ts` fails until all of them agree. Run `npm run prepush` on the new version before merging, since a new compiler can bring new clippy warnings.
- Every release carries two software bills of materials (CycloneDX JSON), generated by the release gate job: `kai_<version>_sbom-npm.cdx.json` (`scripts/generate-sbom.mjs`: the JavaScript packages of the app and the CLI, including devDependencies the CLI build bundles through `noExternal` in `vite.cli.config.ts`, plus the bundled Node.js runtime) and `kai_<version>_sbom-rust.cdx.json` (`cargo cyclonedx`: the crates of the desktop binary). `node scripts/generate-sbom.mjs <dir>` writes the npm one locally.
- The publish job has GitHub sign build provenance for every installer and SBOM (`actions/attest-build-provenance`), after the files are renamed and version-checked. Check a download with `gh attestation verify <file> --repo surajthaqurie/kai-terminal`. This needs the repository to stay public (private repositories need GitHub Enterprise Cloud for attestations); `releaseProvenance.test.ts` fails if the attested and uploaded file lists drift apart.
- `.github/workflows/bundled-node.yml` runs weekly (and on demand): when nodejs.org lists a newer LTS release of the same major line it downloads and checks it, then opens a pull request that changes the file. Merging the PR is what ships it. Enable **Settings → Actions → General → Allow GitHub Actions to create and approve pull requests** once for this to work.
- To move to another major line (for example 24 to 26), edit the file by hand after running the test suite on that Node, then release.

## 2. Installer Formats & Output Locations

Installer packages are generated by `npm run tauri build` in `src-tauri/target/release/bundle/`:

| Operating System | Installer Target | Extension | Output Location |
| :--- | :--- | :--- | :--- |
| **Linux** | DEB Package & AppImage | `.deb`, `.AppImage` | `src-tauri/target/release/bundle/deb/`, `bundle/appimage/` |
| **Windows** | NSIS Setup & MSI | `.exe`, `.msi` | `src-tauri/target/release/bundle/nsis/`, `bundle/msi/` |
| **macOS** | DMG Disk Image & App Bundle | `.dmg`, `.app` | `src-tauri/target/release/bundle/dmg/`, `bundle/macos/` |

## 3. Update Verification & Status

In-app release checking (`Settings > Updates`) queries the public GitHub Releases API (`https://api.github.com/repos/surajthaqurie/kai-terminal/releases/latest`). When a newer release exists, Kai downloads the installer for the platform and package type it was installed with (hosts are allow-listed to GitHub release assets), shows a two-step progress bar ("Downloading", then "Installing in the background"), and installs unattended:

| OS | Unattended path |
| :--- | :--- |
| **Windows** | Detached helper runs the `.exe` (NSIS) or `.msi` silently, deletes the installer, and reopens Kai |
| **macOS** | Helper swaps the `.app` from the downloaded `.dmg` and reopens Kai |
| **Linux** | `.deb` installs via polkit (`pkexec`); an AppImage is replaced in place |

Before anything runs, the download is verified against the release's signed checksums (section 1.3a): a release without valid `SHA256SUMS`/`SHA256SUMS.sig`, a hash mismatch, or a version that is not newer is refused, the file is deleted, and the user is pointed to the release page. Installers are saved in a per-user folder (`%LOCALAPPDATA%\kai\updates`, `~/Library/Caches/kai/updates`, `$XDG_CACHE_HOME/kai/updates` or `~/.cache/kai/updates`), not the shared temp directory.

When no unattended path exists (read-only install location, no `pkexec`) the installer is opened for the user to finish by hand. After the restart Kai reports whether the update worked. Release assets must therefore keep one installer per package type with the usual names (`*-setup.exe`, `*.msi`, `*.dmg`, `*.deb`, `*.AppImage`).

## 4. Production Release Checklist

Before releasing a new version tag:

- [ ] **Run Quality Checks:** Pass all frontend checks (`npm run check`).
- [ ] **Run Backend Unit Tests:** Pass all Rust tests (`cargo test --no-default-features --manifest-path src-tauri/Cargo.toml --lib`).
- [ ] **Run PTY Integration Tests:** Pass integration scenarios (`cargo test --no-default-features --manifest-path src-tauri/Cargo.toml --test pty_integration_tests`).
- [ ] **Run GUI-Feature Security Tests:** `npm run build`, then `cargo test --features gui-test --manifest-path src-tauri/Cargo.toml --test window_acl --test update_verify --test update_flow` (per-window command ACL and updater verification), and `cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings` (lints the real GUI code that `--no-default-features` compiles out).
- [ ] **CI is green for the tagged commit:** the release `gate` refuses a tag whose commit has no green `ci.yml` run (it waits up to 30 minutes for one that is still running). Push the commit to a branch and let CI finish before tagging; a failure on Windows or macOS therefore cannot publish.
- [ ] **Docs match the code:** `SECURITY.md` (the CSP line against `tauri.conf.json`, the capability lists against `capabilities/*.json`, secrets "piped on stdin", what the app contacts on the network), `KNOWN_LIMITATIONS.md` (the verification-scope section) and the "what runs while idle" table in `ARCHITECTURE.md`. Anything a change touched in those areas is updated in the same change.
- [ ] **Bundle size budget:** after `npm run build`, `npm run check:bundle` (gzip limits in `scripts/bundle-budget.json`; the App limit was lowered to 180 kB when the xterm add-ons became lazy; CI runs it too). Raise a limit only on purpose, in the same change.
- [ ] **Bundled Node.js current:** merge or consider any open "bundle Node.js" pull request (section 1.5).
- [ ] **Signing key present:** the `UPDATE_SIGNING_KEY` secret is set (section 1.3a); after publishing, confirm `SHA256SUMS` and `SHA256SUMS.sig` are attached.
- [ ] **Update Version:** Run `npx changeset version` (bumps `package.json` and writes `CHANGELOG.md` from `.changeset/`), then `npm run version:sync`: it copies that version to `package-lock.json`, `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`, `src-tauri/tauri.conf.json`, `kai-website/package.json` and its lock file, and the installer names and tags in `README.md` and `INSTALL.md` (`-- --check` only lists what differs). Add the release's title to `kai-website/scripts/release-titles.json` by hand.
- [ ] **Refresh the website data:** `node kai-website/scripts/sync-changesets.mjs && node kai-website/scripts/sync-docs.mjs`, then `npm run build:website`.
- [ ] **Tag & Push:** Create git tag (`v0.2.3`) and push to trigger automated release publishing on GitHub:
  ```bash
  git tag v0.2.3
  git push origin v0.2.3
  ```
