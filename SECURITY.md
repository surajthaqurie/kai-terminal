# Security Model & Policy

This document describes process execution controls, IPC capabilities, permission handling, and secret policies enforced in Kai Terminal.

---

## 1. Process Launching Controls

- **Direct Argv Execution:** Child processes are spawned using `portable-pty`'s `CommandBuilder` with direct `shell_path` and string arguments. Command line strings are never interpolated through a shell interpreter, preventing command injection vulnerabilities.
- **External Agent Execution Controls (`kai run`):** When executing external coding agents via `kai run`, processes are spawned with `shell: false` across all POSIX platforms (and on Windows unless targeting `.cmd`/`.bat` binaries). This prevents argument injection and shell metacharacter expansion. Windows `.ps1` targets are launched as `powershell.exe -NoProfile -File script.ps1` with an argv array (no shell) and without `-ExecutionPolicy Bypass`, so the user's execution policy still applies. Process timeouts and cancellations trigger POSIX SIGTERM followed by SIGKILL after a 2-second grace period (on Windows, the command runs inside a Job Object created by the desktop binary, and the whole job is stopped, detached descendants included; without the desktop app, `taskkill /PID /T /F` stops the linked process tree). Agent exit codes (success, failure, timeout `124`, cancel `130`) pass through intact and are never overwritten by subsequent background graph sync tasks.
- **Path & Parameter Validation:** `shell_path` and `cwd` are checked before spawning: executable files must exist on disk and possess executable permissions. NUL bytes and oversized paths (>4096 bytes) are rejected.
- **Environment & Working Directory:** The default working directory falls back to `$HOME` / `%USERPROFILE%`. Working directory paths fall back safely rather than auto-creating missing paths or using elevated system folders.

## 2. IPC Boundary & Capabilities

- **Capability Files:** `src-tauri/capabilities/` holds one capability per window class (`default.json` for the terminal windows, `music-pip.json`, `shared-chat.json`), each granting `core:default` plus only the window powers and app commands that class needs (next bullets).
- **Content Security Policy (CSP):** Enforced in `tauri.conf.json`:
  `default-src 'self'; connect-src 'self' ipc: http://ipc.localhost https://api.github.com; script-src 'self'; style-src 'self' 'unsafe-inline'; font-src 'self' data: https://fonts.gstatic.com; img-src 'self' data: <YouTube thumbnail hosts>; frame-src 'self' http://localhost:* <YouTube player hosts>; media-src 'self' blob: <YouTube hosts>` (the real, complete policy is the one in `src-tauri/tauri.conf.json`; `src/__tests__/tauriCsp.test.ts` pins its security-relevant parts).
  What the page itself may connect to is exactly the app backend (`ipc:`) and the GitHub releases API for the update check; the music player is an iframe (`frame-src`), which brings its own network access, so no media or Google host is allowed in `connect-src`. Two residual looseness are known and accepted: `style-src 'unsafe-inline'` (xterm.js and React set inline styles) and `frame-src http://localhost:*` (the music relay page on macOS/Linux is served from a port chosen at run time, so the port cannot be named in a static policy). `script-src 'self'` has no `unsafe-inline` and no `unsafe-eval`.
- **Exposed IPC Commands:** The authoritative list is `APP_COMMANDS` in `src-tauri/build.rs` (it must equal the `generate_handler!` list in `src-tauri/src/lib.rs`; `src/__tests__/tauriCapabilities.test.ts` fails when they drift). No remote code execution interfaces exist; the two Shared Agent commands relay JSON requests to the Shared Agent engine (section 5), whose agents are read-only.
- **Per-window command permissions:** Declaring `APP_COMMANDS` turns on Tauri's ACL for the app's own commands: each gets an `allow-<command>` permission and a window may call it only if its capability file grants it. The terminal windows (`main`, `term-*`, `capabilities/default.json`) are granted every command. The music mini-player (`music-pip.json`) may call only `close_music_pip` and `music_relay_url`; the popped-out Shared Agent chat (`shared-chat.json`) only `shared_agent_request_cmd`, `shared_agent_stop_cmd` and `close_shared_chat_window`. Those two windows embed third-party content, so they cannot start a process (`create_pty`), run an installer, or rewrite agent configuration. A window with no capability can call nothing. This is enforced and tested at runtime in Tauri's mock runtime against the real capability files (`src-tauri/tests/window_acl.rs`, run in CI as part of the GUI-feature security tests). It limits what a compromised secondary window can do; the main window is trusted by design (it runs your shell), so webview script integrity (CSP `script-src 'self'`) remains the boundary for it.
- **Updater integrity:** An update is installed only if it is verified first. Releases publish `SHA256SUMS` and `SHA256SUMS.sig` (a raw Ed25519 signature over those bytes, made in CI with the `UPDATE_SIGNING_KEY` secret). The app embeds the public key (`src-tauri/update-public-key.hex`) and, before anything is launched: requires the release to be strictly newer than the running version (a validly signed older release cannot be replayed); verifies the signature on the checksums; streams the installer into a private per-user folder (not the shared temp directory) while hashing it, with a size cap and https plus allow-listed hosts enforced on every redirect hop; and keeps the file only if its hash equals the signed value for that exact file name. The launch command runs nothing that was not verified in the current session and re-hashes the file immediately before launching. Any failure deletes the file, runs nothing, and tells the user to install from the release page. A release published without `UPDATE_SIGNING_KEY` is therefore installable only by hand. Rotating the signing key requires shipping an app build that embeds the new public key first (see `RELEASE_GUIDE.md`). What this does not cover: someone who holds the signing key, or who can ship a malicious *app build* (the embedded key lives in the app).
- **Executable lookup (Windows):** The CLI, `kai mcp` and the Shared Agent engine set `NoDefaultCurrentDirectoryInExePath=1` in their OWN environment at startup (Node resolves `spawn("git")` and similar in the parent process, so setting it only in a child's environment, as an earlier version did, did not help: a `git.exe`, `cmd.exe` or `powershell.exe` planted in a cloned repository ran). Fixed system tools (`cmd.exe`, `taskkill.exe`, `where.exe`) are spawned by absolute `System32` path. Tools that are meant to follow PATH (`git`, `az`, a configured shell) still resolve through PATH, never the working directory. Rust-side spawns use `Command::new`, which does not search the working directory on Windows.
- **Git Command Boundaries:** Git actions validate relative repository paths against null bytes, path traversal (`..`), leading slashes, and Windows drive letters. Symlinks escaping the repository root are strictly resolved and rejected. Paths are literal file names, never patterns (`GIT_LITERAL_PATHSPECS=1`: a file called `[id].tsx` does not also match `i.tsx`), and a bare `.` is refused as a file path (whole-tree actions are separate, explicit commands). Probes set `GIT_OPTIONAL_LOCKS=0`, so a background status never makes your own `git commit` fail on `index.lock`. Git processes are bounded by an 8-second execution deadline with background stdout draining and child process reaping on timeout. Git is run inside folders the user merely visited (the footer branch badge probes on `cd`), and git honours a folder's own `.git/config`, so every invocation forces `core.fsmonitor=false` (a repository-configured fsmonitor command otherwise runs on `git status`), diffs add `--no-ext-diff --no-textconv`, and probes set `GIT_OPTIONAL_LOCKS=0` so they never take `index.lock` from your own `git commit`. Not neutralised: clean/smudge filter drivers (`filter.<name>.clean`) that a repository's own config defines and its `.gitattributes` references can still run during `status`/`diff`; do not `cd` into repositories you do not trust with a configured filter driver.
- **Folders reported by the shell (OSC 7 / OSC 9;9):** anything that can print to a terminal can write these sequences (a `cat`ed file, a remote `ssh` shell). The page treats them only as a signal and asks the backend for the folder. The backend accepts an OSC 7 report only when its host is empty, `localhost` or this machine's name (a Linux path from a WSL shell, which can never be a local Windows folder, is exempt because WSL reports under its own host name) and, for a path of this OS, only when the folder exists. This stops terminal output from choosing the folder the git panel and new tabs use.
- **Agent Auto-Wire Safety:** `setup_agent_mcp_cmd` only accepts built-in provider ids (never paths) and ignores any launcher the page sends: the command written into an agent's config is resolved by the backend from the installed CLI, so a compromised page cannot persist an arbitrary command there. Configs over 1 MB or with invalid JSON/TOML are never rewritten. The first backup (`<file>.kai.bak`) is the user's original and is never replaced by a later re-wire; the new file is written to a temp file that starts with the original's permissions (a `0600` config stays `0600`; a file Kai creates is `0600`), flushed to disk, then renamed over it.

## 3. User Privileges & Secrets

- **User Privileges:** Kai runs with standard OS user permissions. It does not auto-elevate or run as Administrator/root. Admin privileges are only granted when the user explicitly runs `sudo` or elevation prompts within their shell.
- **No Telemetry or Secret Persistence:** Keystrokes typed into shell sessions, environment variable values, and terminal outputs are never logged to disk or external servers.
- **Integration Credentials:** Signing in to an external service (`kai integration azure`, `kai integration teams`) is opt-in. With the Azure CLI, Kai stores no secret and asks `az` for a short-lived token per session. An access token is kept in the OS secret store (Windows DPAPI, macOS Keychain, Linux Secret Service) or, only if none is usable, in a `0600` file under `~/.kai/credentials`. It is never written to `config.json`, a repository, or an agent's MCP config, never passed as a command-line argument (it is piped on stdin, including from the desktop app), and redacted from error messages. On Windows the DPAPI helper (`powershell.exe -ExecutionPolicy Bypass -EncodedCommand`, a fixed script that runs nothing the user supplied) receives the secret on its stdin, not in argv or its environment. If no OS secret store is usable the store falls back to a `0600` file under `~/.kai/credentials`; on Windows `0600` has no effect and the file inherits the profile's ACL, so it is as private as the user profile. `KAI_ADO_PAT` can supply a token for headless runs.
- **Microsoft Teams Sign-in:** `kai integration teams` uses the browser sign-in (OAuth 2.0 authorization code with PKCE, a public client with no secret). The token set is kept in the OS secret store and never in `config.json`, a repository, an environment variable, an agent's config or Kai's MCP server. `kai teams` is the only consumer, needs a person at an interactive terminal, and `kai teams` and `kai integration teams` refuse to run inside an AI agent's session (process-tree, environment-marker and terminal checks). This is guidance for the ordinary routes, not a sandbox; see `docs/teams-sign-in.md`. Images pasted from the clipboard go to a private per-user temp folder and are removed after a day.
- **Local Settings Storage:** User settings (`kai_user_settings`) and saved workspace tab structures (`kai_workspaces_v1`) store layout information, shell paths, and UI preferences in browser `localStorage`. Command history, typed input, scrollback logs, and credentials are never stored. (An earlier version kept every line typed before Enter, including text typed at no-echo prompts, in `localStorage` under `kai_cmd_history_v1` for a suggestion feature that was never shown; that code is removed and the key is deleted on startup.)

## 4. Project Scanner, Indexer & MCP Security Model

- **Sensitive files behind links:** the sensitive-file filter judges both the name of a directory entry and what it resolves to, in the index scan, in `kai_read_range` / `kai_get_context` path checks, in retrieval and in Code Mode path screening. A link named `notes.txt` that points at `.env` or `id_rsa` is not indexed and cannot be read through the MCP tools. (File links need Developer Mode on Windows; the Linux and macOS CI runs the link tests.)
- **Non-Execution Invariant:** Under no circumstances are indexed project files, build scripts, test suites, or package hooks executed during scanning, indexing, or retrieval. All parsing is passive, static lexical analysis.
- **Path Traversal & Symlink Escapes:** Canonical paths are verified with `fs.realpathSync`. Any symbolic link pointing outside the authorized project root is rejected and never traversed.
- **Default Secret Exclusion:** Sensitive files and credential patterns are filtered by default:
  - Environment files: `.env`, `.env.*`
  - SSH and cryptography keys: `id_rsa*`, `id_ed25519*`, `*.pem`, `*.key`, `*.pfx`, `*.p12`, PKCS#8 / OpenSSL PEM private keys
  - Cloud and API credentials: `credentials.json`, `secrets.json`, `token.json`, `service-account*.json`, fine-grained GitHub PATs (`github_pat_*`), Anthropic API keys (`sk-ant-*`), OpenAI API keys (`sk-*`)
- **Resource Exhaustion Bounds:**
  - File size cap: 512 KB per file.
  - File count limit: 10,000 files per project.
  - Traversal depth limit: 20 directories.
  - Binary files (by extension or null byte check) are skipped.
- **Context Injection & Prompt Isolation:**
  - Prompt templates demarcate untrusted context boundaries with explicit warning headers.
  - Dynamic code fence escaping (`safeCodeFence`) prevents markdown breakout when user source code contains triple or quadruple backticks.
- **Concurrency & Atomic Storage:**
  - Index and metadata writes use atomic temporary file creation followed by rename (`atomicWriteJson`) with Windows retry logic on transient anti-virus locks.
  - Concurrent operations are protected by PID-tracked file locks (`ProjectLock`) and generation guards preventing index corruption or stale candidate overwrites.
  - Dual-copy crash consistency checks (`checkPersistenceConsistency`) detect schema, id, status, or timestamp skew between `meta.json` and `index.json`, triggering a safe rebuild rather than serving corrupted state.
  - Status transitions (`markProjectGraphStatus`) atomically synchronize both `meta.json` and embedded index copies.
- **MCP Stdio Isolation & Stream Protection:**
  - The MCP server operates exclusively over standard input/output (`stdio`) JSON-RPC. It does not listen on network sockets or open network ports. (The only listener Kai ever opens is the opt-in Shared Agent host, section 5.)
  - The code-map tools make no network requests. If a project is connected to an external service (`kai integration azure`), that project's integration tools make outbound HTTPS requests to that service only, with bounded size and time, and expose no write operations unless you turn on write tools for that folder with `kai integration azure --allow-writes` (see `MCP.md`). That switch is stored in the project's private binding file, never in the repository, is refused inside an AI agent's session, is re-checked on every call, and the write tools only comment, create work items, change a work item's state or fields, or open a pull request between existing branches, in the bound project, with your own sign-in. The workflow-rules tool only computes names locally: work item titles are reduced to a safe slug for branch names and are never placed inside a command. A project that is not connected lists none of them.
  - Text returned by an external service is untrusted (other people write it): it is reduced to plain text, size-capped, and every response carries a notice saying so.
  - A project's connection is a private file under `~/.kai/projects/<id>/`, never inside the repository, so cloning a repository cannot switch an integration on or aim it at an organization.
  - All tools are strictly read-only on project sources.
  - All tool arguments resolving file paths enforce strict workspace confinement using `fs.realpathSync`, rejecting unauthorized path traversal and out-of-boundary access.
  - Stream-level line size enforcement (`BoundedLineTransform`) discards requests exceeding 10 MB directly on the byte stream before Node buffers or `readline` can accumulate unbounded memory.
  - Project paths and symbol query arguments containing NUL bytes (`\0`) are strictly rejected.
  - Graph-dependent reads (`kai_search_code`, `kai_find_symbol`, `kai_get_dependencies`, `kai_get_context`) automatically gate freshness and execute a bounded auto-refresh when out of date, reporting verified freshness metrics.
- **Live Staleness Detection & Index Verification:**
  - Context retrieval computes on-the-fly SHA-256 digests of disk sources and compares them against index snapshot hashes. Stale files trigger explicit warnings directing users to re-index (`kai graph update`).
  - Index caching validates `mtimeMs`, `ctimeMs`, and `sizeBytes` to prevent silent corruption or stale reuse across filesystem changes.
- **Prototype Pollution Defense & Input Boundaries:**
  - In-memory index maps and dependency lookups use null-prototype objects (`Object.create(null)`) with explicit `Object.prototype.hasOwnProperty` guards.
  - Task classifier inputs are strictly bounded to 4,000 characters to prevent regex backtracking or CPU exhaustion on oversized prompts.
  - `kai config get` restricts lookups strictly to an approved configuration key allowlist (`ALLOWED_KEYS`).
  - Language server probes validate command names before checking system `PATH`.
  - Storage deletion in `kai remove` validates input project paths and supports clean deletion of orphaned storage by 16-character hexadecimal ID when `meta.json` is missing or corrupted.
- **Privacy-Safe Telemetry:**
  - Local diagnostic metrics are appended to `~/.kai/metrics.jsonl` tracking only execution latencies, token counts, and error codes.
  - The telemetry file automatically rotates at 5 MB (retaining one `.1` generation) to prevent unbounded disk growth.
  - User prompts, indexed source contents, and secret keys are never persisted to metrics logs.

## 5. Shared Agent (agents shared over your network)

Shared Agent lets another Kai Terminal PC chat with this PC's Claude Code or OpenCode, and this PC chat with another PC's. Hosting is always done by Kai Terminal. Other PCs reach it on the LAN, or from anywhere through a tunnel or reverse proxy the person runs themselves (ngrok, Cloudflare Tunnel, a company proxy). It is the only feature that opens a network listener.

**Threat model.** The network is treated as hostile. That includes anyone on the same LAN (sniffing, ARP spoofing, taking over the host's address), the tunnel or proxy provider (it terminates TLS and would otherwise see plain text), anyone on the internet who learns the tunnel address, and a joined PC that misbehaves.

- **Separate process, off by default:** all of it runs in one Node process (`dist/cli/shared-agent.js`) that the desktop app starts on first use and stops when it exits; a closed pipe also ends it. There is no `kai` command for it, and it refuses to start when launched by an AI agent. The webview never reaches the network itself (its CSP is unchanged). Whether sharing is on is never stored: a listener is opened only after a person turns sharing on in the current session, so every restart leaves the PC private.
- **End-to-end encryption (Kai Secure Channel, `kai-sc-1`):** everything after a one-round-trip handshake is encrypted and authenticated between the two Kai processes, whatever carries it. Built only from Node's `crypto`: X25519 key agreement, HKDF-SHA256, AES-256-GCM with per-direction keys, counter nonces, the session id and direction bound into the authenticated data, and a replay window on the host. Fresh ephemeral keys on both sides give forward secrecy. The LAN, the tunnel provider and any proxy see only ciphertext. They also see a session id, the joined PC's id, message sizes and timing, and the caller's address. They never see an invite secret, a key, a PC or host name, a prompt or an answer. TLS on the tunnel is an extra layer, not the protection.
- **Host identity:** the host has a long-lived X25519 identity key, whose private half is kept in the OS secret store. Its SHA-256 fingerprint is part of every invite link. A joining PC refuses a host that can't prove it holds that key (proof is an AEAD confirmation under the new session keys), and sends it nothing. After joining, the key is pinned, so a host whose key changes is refused as an impostor. Both PCs show a **safety code** derived from that key, so people can compare them by voice for extra assurance.
- **Joining:** an invite link is `…/join#<secret>.<host fingerprint>`. The secret is 256 bits and expires after 5, 15 or 60 minutes or, if the host chooses, when sharing stops. It is never sent: the joining PC sends only an HMAC-derived lookup tag, and the secret keys the handshake as a pre-shared key, so only a holder of the link can complete it. The host keeps the tag on disk and the derived key in memory only, so a restart voids every open invite. Wrong attempts are rate limited per address. A joining PC registers a new X25519 key of its own; its private half stays in that PC's OS secret store. Every PC that joins gets a new row on the host with default permissions. A row is never matched by name or address, so an invite can't be used to take over another PC's permissions or history. At most 50 PCs can join. Removing or disconnecting a PC ends its sessions at once.
- **Using a host:** each session must prove the PC's registered key (static-static and static-ephemeral key agreement). Knowing a PC's id gets nothing, and a captured message can't be replayed or altered. There is no bearer token to steal. Sessions end after 15 minutes idle or 8 hours, are capped per PC and overall, and work only from the network they were opened on.
- **Network checks (defence in depth):** the host serves only addresses inside a subnet this PC is directly attached to, or this PC itself. While, and only while, the person has set an internet (tunnel) address, PCs that reach it through that tunnel are served too. A relayed request is recognised by its forwarding headers or the tunnel host name, and never gets the trust of a LAN caller. A PC works only from the kind of network it joined from, and loopback is not a wildcard. Forwarding headers name the internet client only when the tunnel agent runs on this PC; otherwise rate limiting uses the real peer address. Kai never starts a tunnel.
- **Forged calls cannot end a session:** the session id travels in clear text, so a message that fails to decrypt (or arrives from another network) is refused and counted against the sender's address, but does not end the session on its own; a session is dropped only after five consecutive messages fail to decrypt. A real client sends none.
- **Kai Terminal only:** both ends must be Kai Terminal. The host refuses handshakes and calls without the `x-kai-client` header, and Kai refuses replies without `x-kai-service`. Agent Bridge PCs, browsers and other programs are refused. The headers mark the product boundary; the keys above do the authentication. In the clear the host serves only a landing page, `/api/health` (no version, no host details) and the two secure-channel endpoints.
- **What a shared agent can do:** chat only. Claude Code runs with `--tools=` (no tools at all), `--restricted`, `--safe-mode` (none of the host user's CLAUDE.md, skills, plugins, hooks, custom commands or agents), `--disable-slash-commands` and `--strict-mcp-config` (no MCP servers). OpenCode runs its read-only `plan` agent with every permission denied (`"*": "deny"`), both globally and on the agent itself, so tools from MCP servers in the user's global config are refused too. Every run is in a new empty folder. The prompt is written to the agent's stdin, never placed on its command line, and no shell is used (Windows `.cmd`/`.ps1` launchers go through the same quoted no-shell path as `kai <agent>`). Values that reach argv (model, session id) are validated against strict patterns, and a model name must start with a letter or digit so it can never be read as a flag. Only the host chooses the model, since its account pays; a joined PC's request is ignored. Each run has a per-PC time limit (1 to 240 minutes, 10 by default) and a cap on recorded events. Messages are capped at 20,000 characters.
- **Receiving side:** only private-network IPv4 hosts over HTTP, or tunnel hosts over HTTPS, are ever contacted, and redirects are never followed. Replies are capped at 4 MB. `~/.kai/shared-agent/hosts.json` holds only public keys and ids; each joined host's private key goes to the OS secret store. Text from a host is shown as chat output, never executed.
- **What it does not protect against:**
  - A compromised host or joined PC: malware there can read the chat, or use that PC's key.
  - The agent's own provider: prompts still go from the host to Anthropic, or to OpenCode's configured provider, as any use of that agent does.
  - The fact that two PCs are talking, how much they send and when.
  - An invite link that leaks before it is used. Send links over a channel you trust, keep their lifetime short, and cancel unused ones. Comparing the safety code catches a host that is not the one you meant, but not someone who joined with a leaked link: check the **Connected PCs** list.
